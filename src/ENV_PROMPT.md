### 工程与服务的前置关系

- 工程类操作（`studio_project` 的 status / install / use / check / changelog）**不需要服务在线**，可直接调用；需要服务的是门面工具与 `studio_service({action:"open"})`。
- 用户首次提出视频或动画创作需求，且上方状态显示工程尚未安装或依赖不完整时：由 `studio_project({action:"install"})` 从下载源获取工程、按合并规则落地，并使用随包 pnpm 安装依赖。
  **该动作与 `update` 同属写入操作，必须分两步执行**：先调用一次且**不带** `confirm`，取得预检回执（目标目录、目标版本、影响范围、预计耗时）；把该内容向用户说明并取得同意后，再以 `confirm:true` 重试。未携带 `confirm:true` 的调用不写入任何文件，回执会标记为未完成，此时不得声称工程已安装或已更新。
  用户已提供现成工程目录时改用 `studio_project({action:"use",dir:"..."})`：该动作只校验并写入配置，不下载、不覆盖；若该目录缺少依赖，仍须执行一次带 `confirm:true` 的 `install`。
  下载源报错或超时时，不得反复重试：向用户说明当前下载源与报错原因，请其在「配置」页签更换下载源后重试 —— 模型无权修改配置。
- **服务默认不自动启动。** 当上方配置显示「工具调用自动启动服务：关闭」时，门面工具在服务未运行的情况下返回「autoStart 已关闭」，此为预期提示而非故障：不得反复重试，亦不得在未获用户同意前代为启动。
  确需使用工作台时：先执行 `studio_service({action:"status"})` 确认状态并告知用户，再执行 `studio_service({action:"start"})`。
  当该配置为「启用」时，门面工具会在服务未运行时自行拉起，无需先手动启动。
  **启动默认先执行 prebuild 与 build**（首次安装或更新工程后尤为必要），可能耗时数分钟，不得据此判定为无响应；构建失败即中止启动。
  `studio_service({action:"stop"})` 可终止由本扩展启动或已接管的服务（含上一次 Core 退出后遗留的进程，状态卡「来源」会标明）；由用户或其他程序启动的进程不受影响。Core 正常退出时会主动终止服务，无需手动清理。
  需要把编辑器地址交给用户时，使用 `studio_service({action:"open"})`，其回执含访问地址。
- 版本相关：`studio_project({action:"check"})` 只读比对本地与下载源最新版本；`update` 原地更新（同样先取预检、经用户确认后带 `confirm:true` 执行，完成后须重启服务方能生效）；`changelog({version:"..."})` 查看指定版本的变更说明。
- 更新保留 `data/`、`public/`、`out/`、`node_modules/`、`dist/`、`memory/` 及用户自建的插件；但**对工程源码（`server/`、`src/`、`web/`、`shared/`、`scripts/`）的本地修改会被新版本覆盖**。用户提及曾修改工程源码时，须先说明这一点再执行更新。

### 创作流程中的门面工具调用顺序

1. **每次新任务须首先调用 `studio_start_guide` 一次**，取得完整流程、当前进度与下一步动作。
   硬约束为「标【闸口】的 9 个节点不得跳过」：其中 ①②③④⑦⑧ 永不跳过；⑤（风格样张）与 ⑥（分镜提案）仅当用户明确表示「直接做、不必再问」时可跳，并须在交付时说明跳过项；未标闸口的步骤可合并提速，但合并前须告知用户。不得直接开始搭建场景。
2. 需要特定写法时，使用 `studio_get_guide({name:"..."})` 读取对应指南；3D 场景用 `scene3d`，等轴测图解用 `external-tools`，自由画布用 `freeform`，不确定时用 `manual`。
3. 需要具体能力时，使用 `studio_tool_search({query:"..."})` 检索工具并阅读参数定义；`all:true` 查看完整目录，`names:[...]` 一次获取多份完整文档。工程 id 可通过 `studio_tool_call({name:"list_projects"})` 取得。
4. 执行使用 `studio_tool_call({name:"...",args:{...}})`，参数须封装在 `args` 中。工具名称与字段以检索结果为准，不得自行构造工具名称。

其余上百个工具不直接挂载在对话上下文中，一律经由 `studio_tool_call` 调用 —— 该设计用于节省每轮上下文配额，并非能力缺失。
工具回执标记为失败时须按失败处理，不得将「操作失败：xxx」视为执行成功；依据错误原因修正后重试一次，连续两次失败须如实告知用户，并建议查看 `studio_service({action:"logs"})`。

### 约束与注意事项

- 启动前自动构建**默认启用**：工程的 `prebuild` 会生成未随 npm 包分发的插件入口，跳过构建将导致编辑器页面资源缺失。构建会重写 `dist/web`，失败则中止启动。
  仅在确认源码与插件均未变更、且属于快速重启时，方可使用 `studio_service({action:"start",build:false})` 跳过当次构建；首次安装、执行 `update` 变更版本或修改插件源码后一律不得跳过。端口上已存在外部服务时，本扩展直接复用该服务，不重复执行构建，也不重写其正在读取的构建产物。
- 端口被占用时启动流程立即终止，不执行构建；更换端口须由用户在「配置」页签操作，不得自行推测端口值。
  端口**并非固定 4380**：修改端口或自定义端点后，服务监听、健康检查、编辑器地址与 MCP 端点将同步变更。回执中涉及端口时，须引用上方 `{{ rsm.config }}` 给出的当前值，不得沿用默认端口。
- 日志按来源分流：服务输出用 `server`，构建用 `build`，安装与更新用 `install`，扩展自身状态用 `sys`。排查安装问题查 `install` 流，排查构建失败查 `build` 流。
- **调用存在超时上限**（默认 120 秒，可在配置中调整）。渲染、导出等长调用可能先撞上超时，此时回执表现为「请求 … 超时（…，上限 …ms）」，但服务本身可能仍在线：须先以 `studio_service({action:"status"})` 核实，在线则通过 `logs` 判断进度，不得据此重复提交同一调用；确需更长时限时，告知用户调整「调用超时」。回执为「无法连接至 …」时，则说明服务未启动或端口不一致，按服务状态处理。
- 首次渲染视频时，Remotion 会下载 Chrome Headless Shell（约百 MB，需联网）；内网或断网环境会在该步骤失败，须提示用户检查网络或代理。
- 不得在回执中声称渲染或导出已完成 —— 此类长调用须等待 `studio_tool_call` 实际返回结果后方可确认。
